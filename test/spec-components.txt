
# Inline Components

## Standalone inline component

```````````````````````````````` example
:icon-star
.
<p><icon-star></icon-star></p>
````````````````````````````````

## Inline component with content

```````````````````````````````` example
:badge[New]
.
<p><badge>New</badge></p>
````````````````````````````````

## Inline component with content and properties

```````````````````````````````` example
:badge[New]{color="blue"}
.
<p><badge color="blue">New</badge></p>
````````````````````````````````

## Inline component with properties only (no content)

```````````````````````````````` example
:tooltip{text="Hover text"}
.
<p><tooltip text="Hover text"></tooltip></p>
````````````````````````````````

## Inline component within text

```````````````````````````````` example
Click the :button[Submit]{type="primary"} to continue.
.
<p>Click the <button type="primary">Submit</button> to continue.</p>
````````````````````````````````

## Multiple inline components in same paragraph

```````````````````````````````` example
Status: :badge[Active]{color="green"} and :icon-check
.
<p>Status: <badge color="green">Active</badge> and <icon-check></icon-check></p>
````````````````````````````````

## Inline component with markdown content

```````````````````````````````` example
:badge[**bold** text]
.
<p><badge><strong>bold</strong> text</badge></p>
````````````````````````````````

## Inline component with boolean prop

```````````````````````````````` example
:alert{dismissible}
.
<p><alert dismissible></alert></p>
````````````````````````````````

## Inline component with id and class

```````````````````````````````` example
:badge[Text]{#my-id .highlight}
.
<p><badge id="my-id" class="highlight">Text</badge></p>
````````````````````````````````

## Inline component with multiple properties

```````````````````````````````` example
:button[Click]{type="primary" size="lg" disabled}
.
<p><button type="primary" size="lg" disabled>Click</button></p>
````````````````````````````````

## Single-word component name

```````````````````````````````` example
:alert[Warning!]
.
<p><alert>Warning!</alert></p>
````````````````````````````````

## Component does not interfere with URLs

```````````````````````````````` example
Visit https://example.com for more.
.
<p>Visit <a href="https://example.com">https://example.com</a> for more.</p>
````````````````````````````````


## Nested block components where the inner has more colons

Nesting is resolved by matching opening and closing tags, not by requiring the
outer component to carry more colons than the inner one. The canonical spec
example puts the extra colons on the *inner* component.

```````````````````````````````` example
::outer-component
Content in outer

:::inner-component{variant="compact"}
Content in inner
:::

More content in outer
::
.
<outer-component>
<p>Content in outer</p>
<inner-component variant="compact">
<p>Content in inner</p>
</inner-component>
<p>More content in outer</p>
</outer-component>
````````````````````````````````

## Nesting with the same colon count at every level

```````````````````````````````` example
::level-1
  ::level-2

    Content
    ::
  ::
::
.

<level-2>
<level-3>
<p>Content</p>
</level-3>
</level-2>
</level-1>
````````````````````````````````

## A raw HTML block is closed by the component's `::`

Containers are matched before leaf-block content, so the closer belongs to the
component. This needs saying because an HTML block has no closing marker of its
own: types 6 and 7 (`<div>`, `<my-tag>`) run to a blank line, so left to itself
the block would swallow the `::` as HTML text and the component would never
close — taking every following block into it.

```````````````````````````````` example
::note
<div>x</div>
::

after
.
<note>
<div>x</div>
</note>
<p>after</p>
````````````````````````````````

Type 7 covers unknown tags, which is what a bare component-ish tag parses as.

```````````````````````````````` example
::note
<my-tag>
::

after
.
<note>
<my-tag>
</note>
<p>after</p>
````````````````````````````````

An *unterminated* type 2 block (a comment with no `-->`) otherwise runs to the
end of the document, so it loses the closer, `after`, and everything past it.

```````````````````````````````` example
::note
<!-- c
::

after
.
<note>
<!-- c
</note>
<p>after</p>
````````````````````````````````

Each closer ends the HTML block and its own component, so nesting unwinds one
level at a time rather than collapsing.

```````````````````````````````` example
:::outer
::inner
<div>x</div>
::
:::

after
.
<outer>
<inner>
<div>x</div>
</inner>
</outer>
<p>after</p>
````````````````````````````````

The same in JSON output, where the flattening is visible as nesting depth.

```````````````````````````````` example
:::outer
::inner
<div>x</div>
::
:::

after
.
{"nodes":[["outer",{},["inner",{},["html",{"block":true},"<div>x</div>\n"]]],["p",{},"after"]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

A fenced code block is literal, so a `::` inside one is content, not a closer —
the fence still has to close first.

```````````````````````````````` example
::note
```
::
```
::

after
.
<note>
<pre><code>::
</code></pre>
</note>
<p>after</p>
````````````````````````````````

With no component open there is nothing for a `::` to close, so an HTML block
keeps it as text.

```````````````````````````````` example
<div>x</div>
::

after
.
<div>x</div>
::
<p>after</p>
````````````````````````````````


# Component Property Parsing

## Multiple classes are merged

```````````````````````````````` example
:badge[Text]{.foo .bar .baz}
.
<p><badge class="foo bar baz">Text</badge></p>
````````````````````````````````

## Multiple classes merged on block component

```````````````````````````````` example
::alert{.warning .large .bold}
Message
::
.
<alert class="warning large bold">
<p>Message</p>
</alert>
````````````````````````````````

## Single-quoted string values

```````````````````````````````` example
:badge[Text]{color='blue'}
.
<p><badge color="blue">Text</badge></p>
````````````````````````````````

## Mixed props with id, classes, key-value, and boolean

```````````````````````````````` example
:badge[Text]{#myid .cls1 .cls2 key="val" flag}
.
<p><badge id="myid" key="val" flag class="cls1 cls2">Text</badge></p>
````````````````````````````````

## Empty props object

```````````````````````````````` example
:badge[Text]{}
.
<p><badge>Text</badge></p>
````````````````````````````````

## Bind syntax in props

```````````````````````````````` example
:widget{:data='{"x":1}'}
.
<p><widget data="{&quot;x&quot;:1}"></widget></p>
````````````````````````````````

## Object/JSON value in inline component props

```````````````````````````````` example
:component{obj='{"key": "value"}'}
.
<p><component obj="{&quot;key&quot;: &quot;value&quot;}"></component></p>
````````````````````````````````

## Object/JSON value in block component props

The `{...}` scanner has to count brace depth, not stop at the first `}`: an
inner `{` ... `}` inside a quoted value belongs to the value. The inline
scanner already does this, so the two forms must agree.

```````````````````````````````` example
::component{obj='{"key": "value"}'}
x
::
.
<component obj="{&quot;key&quot;: &quot;value&quot;}">
<p>x</p>
</component>
````````````````````````````````

## Object/JSON value in block component props in JSON output

```````````````````````````````` example [no-normalize]
::component{obj='{"key": "value"}'}
x
::
.
{"nodes":[["component",{"obj":"{\"key\": \"value\"}"},["p",{},"x"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## Nested object and array JSON values in block component props

```````````````````````````````` example [no-normalize]
::component{:obj='{"a":[1,2],"b":{"c":3}}'}
x
::
.
{"nodes":[["component",{":obj":"{\"a\":[1,2],\"b\":{\"c\":3}}"},["p",{},"x"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## Object/JSON value in the title form of block component props

The title form (`::name Title {props}`) runs its own copy of the `{...}` scanner,
so it needs the same brace-depth counting as the plain form above.

```````````````````````````````` example
::component Some Title {obj='{"key": "value"}'}
x
::
.
<component title="Some Title" obj="{&quot;key&quot;: &quot;value&quot;}">
<p>x</p>
</component>
````````````````````````````````

## Block component combining key-value, boolean, id and class props

```````````````````````````````` example
::component{multiple="props" bool #id .class}
Content
::
.
<component id="id" multiple="props" bool class="class">
<p>Content</p>
</component>
````````````````````````````````


# Component Slots

## Single named slot

```````````````````````````````` example
::card
#title
Card Title
::
.
<card>
<template name="title">
<p>Card Title</p>
</template>
</card>
````````````````````````````````

## Multiple named slots

```````````````````````````````` example
::card
#header
## Card Title

#content
This is the main content

#footer
Footer text
::
.
<card>
<template name="header">
<h2>Card Title</h2>
</template>
<template name="content">
<p>This is the main content</p>
</template>
<template name="footer">
<p>Footer text</p>
</template>
</card>
````````````````````````````````

## Default content before named slot

```````````````````````````````` example
::card
Default content

#title
Card Title
::
.
<card>
<p>Default content</p>
<template name="title">
<p>Card Title</p>
</template>
</card>
````````````````````````````````

## Explicit `#default` slot

`#default` may be written out, which is useful when mixing the default slot
with named slots. It yields a named `default` template rather than bare
children.

```````````````````````````````` example
::card
#default
This is the **default** slot content.

#footer
Footer content here.
::
.
<card>
<template name="default">
<p>This is the <strong>default</strong> slot content.</p>
</template>
<template name="footer">
<p>Footer content here.</p>
</template>
</card>
````````````````````````````````

## Explicit `#default` slot in JSON output

```````````````````````````````` example [no-normalize]
::card
#default
This is the **default** slot content.

#footer
Footer content here.
::
.
{"nodes":[["card",{},["template",{"name":"default"},"This is the ",["strong",{},"default"]," slot content."],["template",{"name":"footer"},"Footer content here."]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## A one-paragraph slot body with `{attrs}` keeps its paragraph

The AST renderer unwraps a slot body that is exactly one paragraph, but not one
carrying trailing `{attrs}`: the attributes live on the paragraph node, and
`template` is a slot marker the consumer unwraps when mounting, so dropping the
paragraph would drop them. This used to emit a bare `"Prose"`, losing the class
and disagreeing with the HTML renderer, which has always emitted the `<p>`.

```````````````````````````````` example [no-normalize]
::card
#description
Prose {#x .text-lg data-k=1}
::
.
{"nodes":[["card",{},["template",{"name":"description"},["p",{"id":"x","class":"text-lg","data-k":"1"},"Prose"]]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

The same source under the HTML renderer, unchanged:

```````````````````````````````` example
::card
#description
Prose {#x .text-lg data-k=1}
::
.
<card>
<template name="description">
<p id="x" class="text-lg" data-k="1">Prose</p>
</template>
</card>
````````````````````````````````

A body with no attributes still unwraps:

```````````````````````````````` example [no-normalize]
::card
#description
Prose
::
.
{"nodes":[["card",{},["template",{"name":"description"},"Prose"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````


## A YAML block after a slot is not block props

Block props must come immediately after the opening `::component` line, before
any slot definition. Written after a slot, the block is ordinary content — here
a thematic break followed by a setext heading — and the component keeps an
empty prop set.

```````````````````````````````` example
::component
#slot-name
Slot content

---
yaml: props
---
::
.
<component>
<template name="slot-name">
<p>Slot content</p>
<hr>
<h2>yaml: props</h2>
</template>
</component>
````````````````````````````````

## Component frontmatter as YAML props

```````````````````````````````` example
::card

---
icon: star
title: Hello
---

Content here
::
.
<card icon="star" title="Hello">
<p>Content here</p>
</card>
````````````````````````````````

## Component frontmatter needs no surrounding blank lines

The blank lines around the `---` block are optional; the spec spells the block
flush against the opening `::component` line and against the content that
follows it.

```````````````````````````````` example
::card
---
icon: star
title: Hello
---
Content here
::
.
<card icon="star" title="Hello">
<p>Content here</p>
</card>
````````````````````````````````

## Component props keep their YAML types

Objects remain objects, arrays remain arrays, and numbers/booleans are parsed
as their respective types rather than strings.

```````````````````````````````` example [no-normalize]
::component
---
title: My Component
count: 42
enabled: true
items:
  - First item
  - Second item
config:
  theme: dark
  mode: auto
---
Component content goes here
::
.
{"nodes":[["component",{"title":"My Component","count":42,"enabled":true,"items":["First item","Second item"],"config":{"theme":"dark","mode":"auto"}},["p",{},"Component content goes here"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## Deeply structured component props

```````````````````````````````` example [no-normalize]
::data-table
---
columns:
  - name: Name
    field: name
    sortable: true
options:
  striped: true
  pageSize: 10
---
::
.
{"nodes":[["data-table",{"columns":[{"name":"Name","field":"name","sortable":true}],"options":{"striped":true,"pageSize":10}}]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## Component frontmatter with existing props merges both

```````````````````````````````` example
::card{type="info"}

---
icon: star
---

Content
::
.
<card type="info" icon="star">
<p>Content</p>
</card>
````````````````````````````````

## Inline attributes take precedence over component frontmatter

The two prop syntaxes are merged, and a key present in both resolves to the
inline value. The merge has to happen before emission — a component must not
carry the same key twice.

```````````````````````````````` example
::card{title="FromInline" color="inline"}
---
title: FromYaml
icon: star
---
Content
::
.
<card title="FromInline" icon="star" color="inline">
<p>Content</p>
</card>
````````````````````````````````

## Inline attributes take precedence over component frontmatter in JSON output

```````````````````````````````` example [no-normalize]
::card{title="FromInline" color="inline"}
---
title: FromYaml
icon: star
---
Content
::
.
{"nodes":[["card",{"title":"FromInline","icon":"star","color":"inline"},["p",{},"Content"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## Inline props are literal strings, never coerced

Unlike frontmatter props, a plain `prop="value"` attribute is always passed
through as a literal string. Only the `:` prefix opts a prop into JSON /
dot-path handling.

```````````````````````````````` example [no-normalize]
::card{count="42" flag="true"}
x
::
.
{"nodes":[["card",{"count":"42","flag":"true"},["p",{},"x"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````


## A `---` whose body is not YAML opens no props

Block props carry a mapping, so the same body test that gates document
frontmatter gates this position: the classifier looks at the first line of
substance below the fence and requires a `key:` there. `::` is not one, so the
`---` is an ordinary thematic break inside the component. Before the test, the
props parser consumed the closer and the component came out carrying a bogus
`":"` prop.

```````````````````````````````` example [no-normalize]
::card
---
::
.
{"nodes":[["card",{},["hr",{}]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## A paragraph below the fence is content, not props

```````````````````````````````` example
::card
---
Some text
---
More text
::
.
<card>
<hr>
<h2>Some text</h2>
<p>More text</p>
</card>
````````````````````````````````

## An empty or comment-only props block is still consumed

Nothing is lost by consuming it, and Comark resolves both to an empty props
object rather than to markdown -- see `spec-comark.txt`, `## Empty and
comment-only property blocks`.

```````````````````````````````` example
::card
---
# just a note
---
Body
::
.
<card>
<p>Body</p>
</card>
````````````````````````````````

# Bind Props in JSON Output

## Bind prop on an inline component is a JSON-escaped string

```````````````````````````````` example [no-normalize]
:widget{:data='{"x":1}'}
.
{"nodes":[["widget",{":data":"{\"x\":1}"}]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## Numeric bind prop stays a string

```````````````````````````````` example [no-normalize]
:widget{:count="5"}
.
{"nodes":[["widget",{":count":"5"}]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## A bind prop holding a dot-path is preserved verbatim

Resolution of a `:prefixed` value against the render context happens at render
time; the parser's contract is passthrough. The dot-path is neither resolved
nor rewritten, and the `:` stays on the key.

```````````````````````````````` example [no-normalize]
::question{:answer="frontmatter.theAnswer"}
::
.
{"nodes":[["question",{":answer":"frontmatter.theAnswer"}]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## Bind props in a nested component are preserved too

```````````````````````````````` example [no-normalize]
::card{title="Hello" variant="primary"}
:::badge{:color="props.variant" :text="props.title"}
:::
::
.
{"nodes":[["card",{"title":"Hello","variant":"primary"},["badge",{":color":"props.variant",":text":"props.title"}]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## Bind prop values are never coerced, resolved, or dropped

An unknown dot-path and the JSON literals `true`, `5` and `"foo"` all survive
as the exact source text.

```````````````````````````````` example [no-normalize]
:x{:a="unknown.path" :b="true" :c="5" :d='"foo"'}
.
{"nodes":[["x",{":a":"unknown.path",":b":"true",":c":"5",":d":"\"foo\""}]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## A bind prop dot-path loses only its colon in HTML output

```````````````````````````````` example
::question{:answer="frontmatter.theAnswer"}
::
.
<question answer="frontmatter.theAnswer">
</question>
````````````````````````````````

## Bind prop on a block component cannot inject sibling props

```````````````````````````````` example [no-normalize]
::alert{:k='1,"injected":"yes"'}
body
::
.
{"nodes":[["alert",{":k":"1,\"injected\":\"yes\""},["p",{},"body"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

# Malformed Component Frontmatter in JSON Output

Component frontmatter goes through the same YAML-to-JSON writer as document
frontmatter, so the same repair applies: keep what parsed, close what was
opened, and give the failing key an explicit `null`. The prop count the writer
reports is what places the separator before the title / `{props}` that follow,
so before the repair these emitted `{"icon":"title":"My Title"}`.

## Unparseable value in component frontmatter

```````````````````````````````` example [no-normalize]
::card

---
icon: @bad
---

body
::
.
{"nodes":[["card",{"icon":null},["p",{},"body"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

```````````````````````````````` example [no-normalize]

icon: @bad
---

:::
.
````````````````````````````````

## Repaired frontmatter is still separated from inline props


# Zero-Prop Component `{props}` in JSON Output

A non-empty `{...}` string does not guarantee a prop: `{ }` is whitespace only,
and `{=}`, `{.}` and `{#}` are malformed shorthands the props parser skips. The
AST renderer used to emit the separating comma before parsing, so any of these
following a component title or component frontmatter left a trailing comma
inside the props object (`{"title":"T",}`), which `JSON.parse` rejects. The
separator is now emitted only once the parse says something will follow it.

## Whitespace-only props after a title

```````````````````````````````` example [no-normalize]
:::foo T { }
z
:::
.
{"nodes":[["foo",{"title":"T"},["p",{},"z"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

```````````````````````````````` example [no-normalize]
:::foo T {=}
z
:::
.
{"nodes":[["foo",{"title":"T"},["p",{},"z"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## Empty class shorthand after a title

```````````````````````````````` example [no-normalize]

z
:::
.
{"nodes":[["foo",{"title":"T"},["p",{},"z"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````

## Empty id shorthand after a title

```````````````````````````````` example [no-normalize]
:::foo T {#}
z
:::
.
{"nodes":[["foo",{"title":"T"},["p",{},"z"]]],"frontmatter":{},"meta":{"headings":[]}}
````````````````````````````````

```````````````````````````````` example [no-normalize]
z
````````````````````````````````

# Attribute Names Synthesized From Component Keys

A component key becomes an HTML attribute NAME. `render_html_escaped` covers
`& < > "`, which is the escape set for an attribute *value*; a *name* instead
ends at whitespace, `/`, `=` or `>`, so a single key used to be able to
tokenize into several attributes — including a live event handler the document
never wrote. Names now percent-encode `<= 0x20`, DEL, `/` and `=`.

## A frontmatter key cannot synthesize a second attribute

```````````````````````````````` example [no-normalize]
::card

---
x onload=alert(1)//: y
---
::
.
<card x%20onload%3Dalert(1)%2F%2F="y">
</card>
````````````````````````````````

## A frontmatter key cannot be split by a slash

```````````````````````````````` example [no-normalize]
::card

---
a/b: y
---
::
.
<card a%2Fb="y">
</card>
````````````````````````````````

## A frontmatter key cannot be split by a tab

```````````````````````````````` example [no-normalize]
::card

---
"a\tb": y
---
::
.
<card a%09b="y">
</card>
````````````````````````````````

## Punctuation inert inside a name keeps its existing spelling

```````````````````````````````` example [no-normalize]
::card

---
"a'b": 1
"a`b": 2
"a<b>c": 3
"a&b": 4
---
::
.
<card a'b="1" a`b="2" a&lt;b&gt;c="3" a&amp;b="4">
</card>
````````````````````````````````

## A non-ASCII frontmatter key is untouched

```````````````````````````````` example [no-normalize]
::card

---
título: y
---
::
.
<card título="y">
</card>
````````````````````````````````

## An empty frontmatter key is dropped, not emitted as `="v"`

```````````````````````````````` example [no-normalize]
::card

---
"": y
z: w
---
::
.
<card z="w">
</card>
````````````````````````````````

## A `{props}` key cannot synthesize a second attribute either

```````````````````````````````` example [no-normalize]
::card{a/b=c}
body
::
.
<card a%2Fb="c">
<p>body</p>
</card>
````````````````````````````````

## The same holds for inline components

```````````````````````````````` example [no-normalize]
:badge[N]{a/b=c}
.
<p><badge a%2Fb="c">N</badge></p>
````````````````````````````````

Spans, links and images never see such a key: their `{attrs}` run is validated
by the parser first, and a `/` in a name makes the whole run literal text (see
`spec-attributes.txt`, "Malformed Attribute Runs").

```````````````````````````````` example [no-normalize]
**b**{a/b=c}

[t](u){a/b=c}

![i](p){a/b=c}
.
<p><strong>b</strong>{a/b=c}</p>
<p><a href="u">t</a>{a/b=c}</p>
<p><img src="p" alt="i">{a/b=c}</p>
````````````````````````````````

## The AST renderer keeps the same key verbatim

The two renderers agree on which keys are *acceptable* — every key the YAML /
props parser produced is still emitted. The HTML side encodes it into an inert
attribute name; the JSON side is structurally safe already because the key is
a JSON string. A consumer spreading these props onto a DOM element is what has
to reject the name, and `setAttribute` does.

```````````````````````````````` example [no-normalize]
::card{a/b=c}

---
x onload=alert(1)//: y
---

body
::
.
{"nodes":[["card",{"x onload=alert(1)//":"y","a/b":"c"},["p",{},"body"]]],"frontmatter":{},"meta":{"headings":[]}}
.
--format=json
````````````````````````````````
